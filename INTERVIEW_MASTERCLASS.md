## 2. High-Level Architecture Overview

The system is structured as a **Microservices-inspired Monorepo** with 4 distinct pillars:

```
                          ┌──────────────────────────┐
                          │   React Student Client   │ (Port 5173 / HashRouter)
                          └─────────────┬────────────┘
                                        │
                                        ▼
┌─────────────────────────┐  HTTP API   ┌──────────────────────────┐
│   React Admin Client    ├────────────►│  Express Node.js Server  │ (Port 5000)
└─────────────────────────┘             └────────────┬─────────────┘
                                                     │
               ┌───────────────────────┬─────────────┼────────────────────────┐
               ▼                       ▼             ▼                        ▼
       ┌───────────────┐       ┌──────────────┐  ┌───────┐            ┌──────────────┐
       │  MongoDB Hub  │       │  Cloudinary  │  │Resend │            │  FastAPI AI  │
       │   Database    │       │ Cloud Media  │  │Email  │            │ Microservice │
       └───────────────┘       └──────────────┘  └───────┘            └──────────────┘
```

1. **Client Portal (`/client`)**: React SPA for students to register, view, filter, and download materials.
2. **Admin Portal (`/admin`)**: React SPA for administrators to track metrics (users, notes, PYQs, assignments) and publish/delete resources.
3. **Express Backend (`/backend`)**: Central API gateway handling JWT authentication, file stream forwarding to Cloudinary, database CRUD, and email broadcasting.
4. **AI Microservice (`/ai-service`)**: Python FastAPI app for document RAG (PDF extraction -> Chunking -> Vector Embeddings -> ChromaDB Storage -> Context Retrieval -> Groq LLM Response).

## 3. Database Schema Design (MongoDB & Mongoose)

All database models reside in `backend/models/`.

### A. User Schema (`backend/models/User.js`)
- **`fullName`** (`String`, Required): Student's full name.
- **`email`** (`String`, Required, Unique): Used for login & notifications.
- **`dob`** (`Date`, Required): Date of birth, used for identity verification on password resets.
- **`password`** (`String`, Required): Hash generated by `bcryptjs`.
- **`profilePhoto`** (`String`): Hosted Cloudinary URL.
- **`department`** (`String`): Department name.
- **`role`** (`String`, Enum: `["user", "admin"]`, Default: `"user"`).

### B. Resources Schemas (`backend/models/Note.js`, `backend/models/PYQ.js`, `backend/models/Assignment.js`)
- **`title`**: Resource title (e.g. "Unit 1 Data Structures").
- **`subject`**: Subject name (e.g. "DBMS").
- **`department`**: Department (e.g. "Computer", "IT", "Mechanical").
- **`semester`**: Semester number (1 to 8).
- **`fileUrl`**: Secure Cloudinary download URL.
- **`uploadedAt`**: Timestamp.

## 4. In-Depth Code Explanation & Data Flows

Let's trace the core features step-by-step so you can explain *how the code actually works*.

### 1. User Registration & Password Hashing
- **Client**: `Register.jsx` posts `formData` (containing user info & profile photo) to `/api/auth/register`.
- **Backend Flow** in `backend/server.js`:
  1. `multer-storage-cloudinary` uploads the profile photo to Cloudinary under `uploads/profiles`.
  2. `User.findOne({ email })` checks if the email is already registered.
  3. `bcrypt.hash(password, 10)` generates a salt & hashes the plain text password with 10 rounds of hashing.
  4. Saves the user record to MongoDB and returns HTTP status `201`.

### 2. Authentication & JWT Tokens
- **Backend Flow** in `backend/server.js`:
  1. Checks if user exists via `User.findOne({ email })`.
  2. Verifies password using `bcrypt.compare(password, user.password)`.
  3. Creates a **JSON Web Token (JWT)**:
     ```js
     const token = jwt.sign(
       { id: user._id, email: user.email },
       process.env.JWT_SECRET,
       { expiresIn: "1h" }
     );
     ```
  4. Returns `token` and `user` profile data to client.
- **Frontend Storage**: Token is stored in `localStorage`. `PrivateRoute.jsx` protects routes by checking `localStorage.getItem("token")`.

### 3. File Upload & Automated Email Dispatching
When an admin or user uploads notes/assignments via `/api/notes/upload`:
1. **Cloudinary Upload**: `multer` intercepts the file stream and pushes it directly to Cloudinary storage.
2. **MongoDB Record**: A new `Note` or `Assignment` document is created with the returned Cloudinary `fileUrl`.
3. **Notification Broadcasting (`sendEmailToAllStudents`)** in `backend/server.js`:
   - Fetches all student emails using `User.find({}, "email fullName").lean()`.
   - Chunks students into batches of 50 (`CHUNK_SIZE = 50`) to respect API rate limits.
   - Executes parallel email sends via `Promise.allSettled()` using the **Resend API**.
   - Adds a 1-second delay between batches using `setTimeout`.

### 4. Fetching Resources Concurrently (Performance Optimizations)
In `backend/server.js`:
```js
const [notes, assignments, pyqs] = await Promise.all([
  Note.find(query).lean(),
  Assignment.find(query).lean(),
  PYQ.find(query).lean(),
]);
```
- **Why `Promise.all()`?** Runs 3 database queries in parallel instead of sequentially (3x faster response time).
- **Why `.lean()`?** Bypasses Mongoose document instantiation and returns plain JavaScript objects, reducing memory overhead by up to 70%.

### 5. Multi-Step Filtering UI (React Stepper)
In `client/src/pages/Notes.jsx`:
- Uses state `step` (1: Department -> 2: Semester -> 3: Subject -> 4: Download Results).
- `fetchSubjectsAndMaterials` dynamically calls `/api/resources` based on selected department & semester.
- Dynamically extracts unique subjects using `[...new Set(materials.map(m => m.subject))]`.

### 6. AI Microservice: PDF RAG System (FastAPI + ChromaDB + Groq)
Located in `ai-service/main.py`:
1. **PDF Ingestion (`/ingest`)**:
   - `PyPDF` extracts text from uploaded PDFs.
   - `ChunkService` splits text into manageable chunks.
   - `EmbeddingService` generates vector embeddings for each chunk.
   - `ChromaService` indexes chunks & embeddings into **ChromaDB** with metadata (`user_id`, `subject`).
2. **Querying (`/query`)**:
   - Question vector embedding is generated.
   - ChromaDB searches top-5 matching document chunks (`top_k=5`).
   - Context is injected into an LLM prompt.
   - **Groq LLM API** generates an answer grounded in the uploaded PDF context.

## 6. High-Frequency Interview Questions & Expert Answers

Here are the top questions an interviewer will ask about this MERN stack project:

### Q1: "Explain how Authentication and Authorization work in your project."
> **Answer**:
> *"For authentication, when a user registers, their password is salted and hashed using `bcryptjs` before being saved to MongoDB. On login, `bcrypt.compare` verifies the credentials. Once verified, the server generates a signed JSON Web Token (JWT) containing the user ID and email with an expiration of 1 hour.
> On the client side, this token is stored in `localStorage`. We have a `PrivateRoute` wrapper component in React that checks if a valid token exists; if not, it redirects the user to `/login`."*

### Q2: "How did you optimize MongoDB queries for fetching resources?"
> **Answer**:
> *"When a student opens the Notes page, we need data from three collections: `Note`, `Assignment`, and `PYQ`. Instead of fetching them sequentially with `await`, I used `Promise.all()` to fire all three queries in parallel, reducing network latency.
> Furthermore, I chained `.lean()` to all read queries. `.lean()` tells Mongoose to skip creating full Mongoose document instances (with getters, setters, and change tracking) and return plain JavaScript objects instead, which drastically improves memory usage and query execution speed."*

### Q3: "How do you handle file uploads in Express?"
> **Answer**:
> *"We use `multer` combined with `multer-storage-cloudinary`. When a PDF or image is uploaded via a `multipart/form-data` request, Multer streams the file directly to Cloudinary. Cloudinary processes the file and returns a public secure URL (`fileUrl`). We then store this URL string in our MongoDB database rather than storing raw binary files in MongoDB or local disk."*

### Q4: "What happens if you need to send emails to 1,000 students at once?"
> **Answer**:
> *"If we send 1,000 emails concurrently with `Promise.all`, we risk exceeding API rate limits or overwhelming server memory. To solve this, I implemented batching in `sendEmailToAllStudents`.
> We slice the email array into chunks of 50. For each chunk, we trigger sending via `Promise.allSettled()`—which ensures that even if one email fails, the rest continue. We also introduce a 1-second pause (`setTimeout`) between chunks to maintain API rate compliance."*

### Q5: "What is RAG and how does your Python AI service work?"
> **Answer**:
> *"RAG stands for Retrieval-Augmented Generation. In our `ai-service`, built with FastAPI, when a student uploads a textbook PDF, we extract text and split it into chunks. Each chunk is converted into a numerical vector embedding and saved into **ChromaDB**, an open-source vector store.
> When a student asks a question, we convert the question into an embedding, search ChromaDB for the top 5 most semantically relevant text chunks, pass those chunks as context into a prompt, and send it to **Groq's LLM** to generate an answer."*
